# Attune — working agreement

Read this first, every session. It exists so a new session starts where the
last one stopped instead of relearning the project.

**Ellie is the founder and is not a developer.** Explain in plain terms, give
copy-pasteable commands one at a time, and never assume familiarity with git,
terminals or build tools. If something would be faster a different way, say so
rather than waiting to be asked.

**Ellie writes all customer-facing copy.** Every word a customer reads is
hers. **Carolina reviews after publication**, not before, so copy is never
blocked waiting on her. Neither of them is the LMFT.

This matters for routing. Do not hold a copy gap for review, and do not write
customer-facing copy yourself to fill one. Name the gap precisely, say what
shape the missing copy needs to be, and leave it for Ellie.

---

## What this is

A couples assessment platform. Two partners answer independently, and the
product shows them the gap between their answers.

- **Site:** attune-relationships.com (React + Vite on Vercel, auto-deploys on push to main)
- **App:** `attune-app/` (Expo SDK 57, React Native, iOS first)
- **Database:** Supabase
- **Repo:** github.com/ebspencer16-eng/Attune

## Non-negotiables

**Editorial voice, for anything a customer reads.** Short declarative
sentences. No em dashes. No hedging (perhaps, might, it seems). No AI tells
(delve, navigate the complexities, leverage, robust). Neither end of any
dimension is better than the other; the gap is the subject. Couple type is a
dynamic, not a diagnosis. When in doubt, write it shorter, then cut a word.

**Never run database writes.** Deliver SQL as a numbered migration in
`supabase/migrations/`. Ellie runs it in the Supabase SQL Editor herself. This
is deliberate and she owns it.

**Never commit secrets.** Not tokens, not keys, not in code, docs or commit
messages. `attune-app/.env` is gitignored and stays that way.

**Never push code that has not built.** `npm run check` and `npx vite build`
for the site. For the app, run it in the simulator.

**The app does not sell.** Get Started opens the website in the system browser.
An app that builds a cart and hands it to external payment is what Apple
rejects for. See `app/ONBOARDING.md`.

**The app never scores anything.** Results come from `/api/results` already
computed. Two scorers drifting apart is how this product starts lying to
people.

## The failure that keeps happening

Almost every serious bug here has been the same shape: **one rule maintained by
hand in several places, where nothing checks that they agree.**

Package inclusion lived in four places. The exercise list lived in a dozen.
Auth header casing differed between endpoints. A column existed on one table
and was selected from another. Each looked fine in isolation and failed
silently in combination.

So: **derive, do not restate.** Before adding a second copy of any rule, ask
whether it can read the first. If it genuinely cannot, add a gate.

## Rules

Each rule is one line. An id with an arrow (→ G3) has its mechanism, commands
and examples in `docs/lessons.md` under the same id. Read the entry before
working in that area.

### Gates

`npm run check` runs every gate; `npm run build` runs them first. `npm run
smoke` (several minutes, so not in check) builds, serves, and in Chrome renders
every results section and app view, every static page including checkout, and
drives all five exercises to completion. Its section list derives from
`RESULTS_SECTIONS`. Its counts are printed by the run, not written here.

- G1. A gate that passes for the wrong reason is worse than none. Plant the bug it catches and watch it fail.
- G2. A fixture mirroring an existing one means you are writing a second version of a rule. Split gates by what they check, not how. → G2
- G3. A gate matching a literal name is blind to anything reached through a registry. Resolve the indirection; count calls to the gateway. → G3
- G4. A gate encodes a rule, not the current state: name the promise and say what it does not cover.
- G5. Plant four forms every time: named outright, destructured, through a list or lookup, assigned a line earlier. → G5
- G6. When a rule cannot be shared, the gate executes the copy that ships, and throws if it cannot find it. → G6
- G7. Gates die by matching a name instead of what follows it, and by `if (false)`. Plant both. → G7
- G8. A plant that changed nothing proves nothing: assert the needle occurs exactly once, outside comments. → G8
- G9. Test thresholds a hundredth either side, and give each compared implementation data from its own side. → G9
- G10. Ask what a count counted. A non-recursive walk or one-surface scope is a blind spot unless stated beside it. → G10
- G11. A file that says it is safe to paste must be proved runnable; `check-schema-runnable` holds schema.sql. → G11
- G12. Blank comments before a gate or script scans code. → G12
- G13. A gate nothing runs is not a gate. `check-gates-run.mjs` fails on a `check-*.mjs` neither check nor smoke names.
- G14. No escape hatches: a gate never counts an excused failure as a pass.
- G15. A constant that exists is not a thing that is drawn. Check what the code does with the name.
- G16. Prefer behavioural gates that run code and compare answers. A gate that matches too much is not the safe direction.
- G17. A scanner looking for a string also resolves `const NAME = '...'`.
- G18. Type a gate's thresholds out in the gate. Reading them from the module under test compares it with itself.
- G19. Match a path with its separator: `[^'"]*alignment.js` matches `comm-alignment.js`.
- G20. Drive the second branch, not just the first leaf. → G20
- G21. Compare two implementations by output over varied inputs, never by their inputs. → G21
- G22. Before writing a gate, find the one that encodes the rule and widen it to every surface.
- G23. Print a gate's baseline. Drive each view at a package that owns it, and report unrenderable as not rendered. → G23
- G24. A gate testing navigation moves inside the page; reloading resets the state under test.
- G25. Dispatched clicks carry clientX/clientY at the element's middle. Wait before reading; after a click, check you did not navigate.
- G26. Give a check a `data-` handle to measure; ask `elementFromPoint` for z-order and for clipping.
- G27. Before believing a harness measurement, check the harness reproduces the page's structure.
- G28. Check a promise everywhere it is made. Gate values that agree today; nothing watches them.
- G29. When Ellie reverses an instruction, keep both quotes in the gate.
- G30. Comparing markup is not enough; a gate also does what the markup is for (`check-mobile-menu` clicks the button).
- G31. A rule about values is run three ways: it happens, it is not undone, it does not happen for free. → G31
- G32. A review document is judged as committed: the gate reads it, regenerates, and compares. No generator ahead of it in the chain.
- G33. A gate whose subject is a value reads the value, not the count.
- G34. A gate about when something happens lets it happen (stubbed fetch, count the calls).
- G35. A rule enforced on one surface is not enforced; the admin has its own `check-admin-control-names.mjs`.
- G36. A measurement must exclude the control it reads (scrape a tile's body, not its card).

## Verification, non-negotiable

**Never claim a fix without evidence.** Show the diff, the test output, or a
screenshot.

**Verify the result, not the intent.** Edits by string-match have silently
matched nothing more than once while being reported as applied. Read the file
back.

**When it crosses a network boundary, ask the network first.** A 307 from the
apex domain to www once stripped the auth header; one `curl` found it after
four rounds of reading code.

**Test the real path, not the demo path.** `?demo=1` strips add-ons.

## App development

Everything the app calls is built and tested: `/api/home` (26-case priority
engine), `/api/results`, `/api/notes`, `/api/posts`, `/api/notifications`,
`/api/tool-data` (the checklist, the budget and the workbook file).

Specs: `app/SCREENS.md` (screen by screen), `app/ONBOARDING.md` (get started
through first dashboard), `app/README.md` (stack decisions, bootstrap).

```bash
cd attune-app
npx expo start --ios      # add --clear when a change does not appear
```

Identifiers: Team `HX5FX68K6L`, bundle `com.attunerelationships.app`. The API
base URL is `https://www.attune-relationships.com`. **Keep the www.**

**Builds go through EAS.** `attune-app/eas.json` has three profiles;
`production` reaches TestFlight and auto-increments the build number. Ellie
runs build and submit herself (her Expo and Apple logins); `app/TESTFLIGHT.md`
is her walkthrough. The two public Supabase values are EAS environment
variables.

**Everything runs in the app after purchase.** Ellie: "Ideally, a user
purchases online then downloads the app and only uses the app from that
point." The checklist and budget run against `/api/tool-data`, the workbook
tile hands over the file, profile setup is in the app (`/api/create-profile`
takes the id from a bearer token), and In Practice posts are read in the app.
Static In Practice pages still open in the browser. `check-app-does-not-sell.mjs`
forbids prices, checkout routes and the add-on purchase view in app source.
`check-budget-mirror.mjs` runs the app's copy of the budget arithmetic, which
updates as you type, against the website's.

The results nav comes from `resultsNav` in `api/_lib/results-sections.js`;
`check-results-coverage.mjs` fails if the server sends a section the app cannot
draw. Alerts: six kinds with copy in `api/_lib/notifications.js`, four raised,
recorded in `api/_lib/notification-triggers.js`, drawn as rows at the top of
the home tile. `new_post` and `results_ready` are deliberately not raised,
because the home screen already has cards for both. `check-notification-reach.mjs`
holds them.

Not built: Highlights beyond the storycards, tab-bar badges (`/api/home` sends
`badges` and nothing reads it), and Notes filtering by source, author, or
highlight versus commentary.

**This section goes stale.** A stale map is worse than none, because every
session reads it first. Check a line before repeating it.

## Ending a session

Leave the tree clean and pushed. If work is unfinished, append a short "where I
stopped" note to `HANDOFF.md`: what is done, what is half-done, what the next
step is. Ellie should never have to reconstruct state from a diff.
